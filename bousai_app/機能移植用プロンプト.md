# 防災アプリ機能の移植プロンプト

以下の区切り内を、そのまま移植先システムのAIへ一度だけ入力してください。

---

あなたは既存アプリを調査して機能を安全に統合するシニアエンジニアです。以下の要件を、移植先のフレームワーク、既存データ、認証方式、UI規約に合わせて実装してください。計画だけで止まらず、必要なコードを変更し、動作確認まで完了してください。対象は本書の防災機能に限り、既存システム全体を作り直さないでください。

## 目的

災害対策本部の職員が市内状況をすばやく把握し、避難所の位置・開設状態を確認し、住民向けの指示を作成・更新・発信できるようにする。

## 1. 共通ナビゲーション

- 既存画面からホーム、避難所検索、避難所管理、指示・発信ボードなどへ移動できる共通メニューを設ける。
- ヘッダーに現在画面名を表示し、メニュー内でも現在ページを視覚的・アクセシブルに示す。
- 既存の認証、ルート、遷移を維持する。メニューはキーボード・モバイルでも操作可能にする。

## 2. 避難所マップと場所検索

- ホームに地図を表示し、緯度・経度が有効な避難所だけをマーカー表示する。既存の地図ライブラリがあれば再利用し、なければLeafletとOpenStreetMapを使用する。
- マーカー色は「開設中=緑」「未開設=グレー」「状態未登録=黄」とする。凡例を置き、マーカー選択時に施設名・住所・開設状況を確認できるようにする。
- マーカーの範囲に地図を調整する。欠損・不正座標を推測で補完せず、地図上に出さずに未登録件数として知らせる。
- 管理者向け避難所管理画面では、地図クリックによる位置指定に加え、施設名または住所から候補地点を検索できるようにする。
- 検索地域（都道府県・市区町村）を指定できるようにする。候補を最大5件程度、施設名・住所・検索地域からの距離付きで一覧表示し、同じ建物名や同名地名を地図上の複数ピンで見比べられるようにする。
- 地域中心点が得られる場合は近い候補を優先し、遠方の同名候補を除外する（既定の近傍範囲は50km程度。移植先に適した設定があればそれに合わせる）。候補なし・検索失敗を明確に表示する。
- 候補の選択は地図を移動して入力欄へ座標を入れるだけとし、保存は利用者が登録・更新ボタンを押した時に行う。検索しただけで施設データを変更しない。
- 既存施設の座標・開設状態も編集できるようにする。座標を施設名から決めつけて登録しない。
- 外部ジオコーダーを使う場合は提供元の利用条件・レート制限を守り、手動検索、適切なリクエスト間隔、短期キャッシュ、User-Agent、タイムアウト、接続失敗処理を設ける。日本国内の施設検索では国土地理院地名検索等を優先し、必要なら別サービスへフォールバックする。候補には検索元を示し、取得できない場合も地図クリックで指定できるようにする。

避難所データは既存形式を優先し、必要なら次のような属性を追加する。

```json
{
  "id": 1,
  "name": "避難所名",
  "address": "住所",
  "latitude": 35.0,
  "longitude": 140.0,
  "status": "開設中"
}
```

`status`は「開設中」「未開設」を基本とし、既存値・欠損値は未登録として扱う。

## 3. 気象・災害情報表示

- ホームに気象警報・注意報と災害情報一覧を表示する。既存の情報源（気象庁、指示ボード、道路・現地状況など）を調査し、利用可能なソースを統合する。
- 一覧は受信日時の新しい順にする。タイムゾーンを正しく扱い、利用地域の時刻で日時・情報種別・内容・状態・情報元を表示する。
- 気象、避難、道路、対応状況などで絞り込める選択欄を設け、絞り込み後も新しい順を維持する。
- 災害種別に応じた分かりやすいアイコン（雨、風、水位、雪、地震、避難所、道路など）を付け、サイズ・配置・凡例を統一する。アイコンだけでなく文字ラベルも付ける。
- 最終更新日時、手動更新ボタン、自動更新（標準10分間隔）を設ける。更新中、情報なし、取得失敗を区別し、取得失敗を「災害なし」と誤表示しない。
- 信頼できる情報源がない種類について架空データを作らない。ソース未接続・取得失敗を明示する。

### 気象庁データを利用する場合

- 画面の対象地域と都道府県・市区町村コードを照合する。青森市の場合は青森県`020000`、青森市`0220100`。`140000`は神奈川県なので青森市に使わない。
- 現行データの取得先とJSON構造を確認し、旧形式と新形式を混同しない。複数報がある場合、対象市区町村を含む報告のうち`reportDatetime`が最も新しいものを選ぶ。配列順を時刻順と仮定しない。
- 「発表」「継続」の情報を現況として扱い、「解除」「発表警報・注意報はなし」を継続中の警報として残さない。

## 4. 指示作成・住民向け発信

- 既存の指示・発信ボードがあれば同じデータを使い、ホーム用の重複データを作らない。
- 指示の作成・編集機能がない場合は、既存認証を使う管理者向け入力フォームを追加する。内容、対象（住民／職員など）、必要に応じた避難先、状態、作成・更新日時を登録・更新できるようにする。
- 状態は既存仕様に合わせる。未定義なら「下書き」「発信中」「解除／完了」を区別し、状態変更の履歴または更新日時を残す。権限のない利用者からの作成・編集は拒否する。
- ホーム上部に緊急のお知らせ欄を設け、発表中の気象情報と未解除の住民向け指示を新しい順で表示する。内容、種別アイコン、受信日時、避難先、災害情報一覧への詳細リンクを含める。
- 解除・完了・取消済み情報は履歴一覧に残してもよいが、緊急欄から除外する。住民に向けて表示する情報は対象が住民で、かつ有効状態のものだけにする。
- 緊急情報がない場合は明示的な空状態を表示し、データ取得失敗とは区別する。

## 画面構成

ホーム画面は次の順を基本とする。

1. 共通ヘッダー（現在画面名・ナビゲーション）
2. 緊急のお知らせ
3. 避難所マップ・開設状態の凡例・未登録件数
4. 対象地域の気象警報・注意報
5. 災害情報一覧（種別絞り込み、受信日時、最終更新、手動更新）

避難所の場所検索・位置・開設状態の登録・更新は、認証された避難所管理画面から行う。

## 品質要件

- 実装前に既存コード、データモデル、ルート、認証、UIを調べ、既存の設計・命名・画面遷移に合わせる。無関係な機能やユーザーデータを置換・削除しない。
- 動的表示はテンプレートのエスケープまたはDOMの`textContent`を使い、未検証文字列をHTMLへ連結しない。
- 不正JSON、通信失敗、欠損・不正な座標や日時に耐える。未確認状態を「開設中」と扱わない。
- PC・モバイルで表示が重ならず、ラベル・キーボード操作・アクセシビリティ属性を用意する。
- 検索候補は確認・選択しやすくし、候補選択と保存操作を分ける。
- 必要最小限のファイルを変更し、既存データを破壊的に書き換えない。

## 完了条件

- 地名検索で候補が住所・距離付きで表示され、地図上で比較・選択できる。選択後に保存すると座標が永続化され、ホーム地図に正しい開設状態のピンが表示される。
- 既存避難所の座標・状態を更新でき、再表示後も保存される。未登録座標を推測で描画しない。
- 管理者だけが指示を作成・更新でき、対象・状態に応じて住民向けホーム表示が切り替わる。
- 複数時刻の災害情報を使ったテストで新着順になり、解除済み情報が緊急欄から消える。
- 種別絞り込み、手動・自動更新、候補なし、外部サービス失敗、一覧の空状態が確認できる。
- 各画面へ移動でき、現在画面が識別できる。
- 変更箇所に対するテスト、構文・型チェックまたはスモークテストを実行し、結果と未接続の外部データソースがあれば報告する。

既存システムの調査を開始し、上記の完了条件を満たすまで実装・検証を続けてください。
